# 企业级 OA 系统设计文档

## 1. 文档定位

本文档用于设计一套面向 1000+ 用户规模企业的 OA 系统。系统采用 Web 响应式架构，不对接企业微信、钉钉、飞书、LDAP、AD、外部 SSO 等第三方平台，账号、组织、权限、流程、消息、规则、审计等能力全部由系统自建。

本方案不是简单 MVP，而是按企业级完整 OA 平台进行设计。设计重点不是堆功能，而是先建设稳定的平台底座，再在底座上承载请假、报销、用章、采购、合同、会议室、资产、办公用品、文件资料、公告、报表等业务模块。

适用目标：

- 项目立项与需求评审。
- 产品原型与页面设计。
- 技术架构与数据库设计。
- 开发任务拆分。
- 测试验收与上线准备。

## 2. 项目目标

### 2.1 建设目标

- 建设统一的企业内部办公入口。
- 支持 PC、平板、手机浏览器响应式访问。
- 支持 1000+ 用户规模稳定运行，预留 3000-5000 用户扩展空间。
- 建设组织、人员、岗位、职级、直属上级等企业主数据。
- 建设统一权限中心，支持菜单、按钮、接口、数据、字段、附件和临时授权。
- 建设通用流程审批能力，支撑复杂审批、可配置流程、流程进度查看和提醒。
- 建设规则配置中心，避免金额阈值、上下班时间、审批规则等写死在代码中。
- 建设统一消息、待办、公告、文件、审计、报表和运维能力。
- 让系统既“功能完整”，又“好用、少填、少找、少等、可追踪”。

### 2.2 设计原则

- 平台底座优先：组织、权限、流程、规则、消息、文件、审计先设计稳定。
- 后端强校验：前端控制体验，后端保证权限、安全和数据边界。
- 历史可追溯：人员离职、部门调整、流程改版、规则变化不能破坏历史单据。
- 配置优先：企业制度、流程条件、时间日历、金额阈值、编号规则尽量配置化。
- 体验优先：高频场景要少步骤、少填写、少等待、少犯错。
- 复杂有边界：做企业级可配置 OA 平台，不做无限扩展的低代码平台。

## 4. 总体架构

### 4.1 架构概览

```text

        ↓
前端 Web 应用（Vue 3 + TypeScript）
        ↓
Nginx / 静态资源 / 反向代理
        ↓
后端 API 服务（Spring Boot）
        ↓
业务模块层
        ↓
平台底座层
        ↓
MySQL / Redis / Flowable / 文件存储 / 日志 / 定时任务
```

## 5. 用户、组织与人员

### 5.1 用户规模

- 注册用户：1000+，预留 3000-5000 扩展。
- 日常在线用户：100-300。
- 高峰场景：上班登录、集中审批、月底报销、公告发布、批量导出。

### 5.2 内置角色

| 角色 | 说明 |
| --- | --- |
| 超级管理员 | 系统最高权限，负责初始化和最高级配置 |
| 系统管理员 | 维护用户、组织、角色、权限、字典和系统参数 |
| 流程管理员 | 维护流程模板、流程版本、节点规则和异常流程 |
| 规则管理员 | 维护金额阈值、工作时间、超时规则、编号规则等 |
| 普通员工 | 发起申请、查看本人数据、处理本人待办 |
| 部门负责人 | 审批部门相关流程，查看授权部门数据 |
| 人事专员 | 管理人员档案、请假规则、组织变更 |
| 财务专员 | 处理报销、借款、付款、费用复核 |
| 行政专员 | 管理公告、用章、会议室、资产、办公用品 |
| 合同管理员 | 管理合同申请、归档、到期提醒 |
| 审计人员 | 查看审计日志、关键操作记录和导出记录 |
| 企业领导 | 查看授权范围内统计报表和流程数据 |

### 5.3 组织人员能力

组织能力：

- 多级组织树
- 部门新增、编辑、停用、排序
- 部门负责人设置
- 部门合并、拆分、改名记录
- 组织变更历史

人员能力：

- 新增员工
- 编辑员工
- 启用、停用、离职、返聘
- 员工编号
- 主部门、兼职部门
- 岗位、职级
- 直属上级
- 试用、正式、离职状态
- 批量导入、导出
- 通讯录搜索

关键细节：

- 部门和员工不建议物理删除。
- 历史单据必须保存申请人、部门、岗位快照。
- 员工离职时需要处理待办、委托、资产、文件权限、角色权限。
- 部门调整不应影响历史流程展示和历史报表口径。

## 6. 权限中心

### 6.1 权限类型

- 菜单权限：控制页面入口。
- 按钮权限：控制新增、编辑、删除、导出、审批等操作。
- 接口权限：控制后端 API 访问。
- 数据权限：控制用户能查看哪些数据。
- 字段权限：控制字段可见、可编辑、必填、脱敏。
- 附件权限：控制附件预览、下载、删除。
- 临时授权：指定时间范围内授予某些能力。

### 6.2 数据权限范围

| 数据范围 | 说明 |
| --- | --- |
| 仅本人 | 只能查看本人发起、处理或相关数据 |
| 本部门 | 查看当前主部门数据 |
| 本部门及下级部门 | 查看当前部门与子部门数据 |
| 指定部门 | 查看管理员指定部门范围 |
| 指定人员 | 查看指定人员相关数据 |
| 全公司 | 查看全部数据 |
| 动态业务范围 | 根据发起、审批、抄送、业务归属动态判断 |

### 6.3 权限细节

- 审批权限与数据查看权限必须分离。
- 用户能看某条单据，不代表能审批该单据。
- 附件权限不能简单继承页面权限，敏感附件要单独控制。
- 导出权限必须单独控制并写审计日志。
- 支持权限预览，查看某用户最终能看到什么。
- 支持权限对比，比较两个角色或两个用户权限差异。
- 支持权限复制，从已有角色复制到新角色。
- 临时授权到期后自动回收。
- 高危权限变更需要提醒或审批。

## 7. 通用流程审批引擎

### 7.1 选型

建议采用：

```text
Flowable + 自研 OA 流程适配层
```

理由：

- Flowable 基于 BPMN 2.0，适合复杂审批、条件分支、会签、并行、历史追踪。
- 与 Spring Boot 集成成熟。
- 支持流程定义、流程实例、用户任务、候选人、候选组、变量、历史记录。
- 比完全自研风险更低。
- 比把 BPM 平台直接暴露给业务更可控。

不建议完全自研复杂流程引擎，因为会签、或签、条件分支、驳回、撤回、版本、并发和历史追踪很容易被低估。

### 7.2 分层设计

```text
业务模块
  ↓
OA 流程服务层
  ↓
权限校验 / 表单快照 / 规则计算 / 消息通知 / 审计日志
  ↓
Flowable 引擎
  ↓
Flowable ACT_* 表 + OA wf_* 表 + 业务表
```

原则：

- 业务模块不直接调用 Flowable API。
- 前端不感知 Flowable 内部表和内部 ID。
- Flowable 负责“流程怎么走”。
- OA 流程服务层负责“谁能看、怎么填、怎么提醒、怎么审计、用户怎么看得懂”。
- 业务单据状态和流程实例状态必须在事务上保持一致。

### 7.3 支持能力

流程配置：

- 流程模板
- 流程版本
- 发起节点
- 审批节点
- 条件节点
- 抄送节点
- 会签节点
- 或签节点
- 自动节点
- 结束节点

审批人规则：

- 指定人员
- 指定角色
- 部门负责人
- 直属上级
- 连续多级上级
- 发起人自选审批人
- 表单字段指定审批人
- 流程管理员兜底

审批动作：

- 保存草稿
- 提交
- 通过
- 驳回到发起人
- 驳回到指定历史节点
- 撤回
- 作废
- 加签
- 转交
- 委托
- 催办
- 抄送
- 终止

### 7.4 流程进度查看

系统必须提供流程进度查看能力。

展示内容：

- 流程时间轴
- 流程图高亮
- 当前节点
- 当前处理人
- 下一步预估
- 已处理节点
- 未开始节点
- 审批意见
- 附件记录
- 超时状态
- 催办记录
- 流程版本

示例：

```text
已提交：张三 / 技术部 / 2026-04-28 09:00
  ↓
已通过：直属上级 李四 / 2026-04-28 10:15
  ↓
处理中：财务复核 王五 / 剩余 6 小时
  ↓
未开始：总经理审批
  ↓
未开始：归档完成
```

角色可见范围：

- 申请人可查看本人发起流程的完整进度。
- 审批人可查看审批所需字段、历史意见和后续路径。
- 抄送人只能查看被抄送范围内信息。
- 管理员可查看流程运行状态和异常信息。
- 无权限人员不能通过流程 ID 越权查看进度。

### 7.5 流程提醒

提醒类型：

- 提交前提示预计审批路径。
- 提交后提示已提交并提供查看进度入口。
- 生成待办后提醒审批人。
- 临近超时提醒审批人。
- 超时后提醒审批人、上级或流程管理员。
- 催办后提醒审批人。
- 通过、驳回、撤回、终止后提醒申请人。
- 流程配置错误、找不到审批人、审批人离职时提醒流程管理员。

提醒渠道：

- 站内消息
- 首页待办数量
- 顶部消息角标
- 审批详情页状态提示
- 定时任务生成的超时提醒

### 7.6 流程异常

必须处理：

- 找不到审批人
- 部门负责人为空
- 审批人离职
- 审批人等于发起人
- 审批人长期未处理
- 流程配置错误
- 会签中某审批人离职
- 或签任务被重复处理
- 撤回和审批同时发生

兜底规则：

- 找不到审批人时转交流程管理员。
- 审批人等于发起人时可跳过或上浮一级。
- 离职人员待办支持批量转交。
- 超时支持提醒、升级和流程管理员干预。

## 8. 规则配置中心

### 8.1 定位

公司规定不应写死在代码里。金额阈值、上下班时间、节假日、审批超时、编号规则、报销标准、合同到期提醒、文件大小、导出上限等都应由规则配置中心或系统参数维护。

规则配置中心解决：

- 谁可以设置公司制度。
- 规则什么时候生效。
- 历史单据是否受新规则影响。
- 流程引擎如何读取规则。
- 表单如何校验和提示。
- 规则变更如何审计和回滚。

### 8.2 谁来设置

| 规则类型 | 维护角色 | 示例 |
| --- | --- | --- |
| 系统参数 | 系统管理员 | 密码规则、文件大小、会话超时 |
| 组织规则 | 人事管理员 | 上下班时间、工作日历、请假类型 |
| 流程规则 | 流程管理员 | 审批节点、金额阈值、超时规则 |
| 财务规则 | 财务管理员 | 报销类型、报销上限、付款状态 |
| 行政规则 | 行政管理员 | 用章类型、会议室规则、资产归还期限 |
| 合同规则 | 合同管理员 | 合同到期提醒、合同分类、金额阈值 |
| 审计查看 | 审计人员 | 查看规则变更记录，不直接修改 |

### 8.3 配置化清单

不建议写死的内容：

| 分类 | 配置项 |
| --- | --- |
| 组织人事 | 员工状态、岗位类型、职级、部门负责人规则 |
| 工作时间 | 上班时间、下班时间、午休、工作日、节假日、调休日 |
| 请假规则 | 请假类型、最小请假单位、附件要求、超过几天追加审批 |
| 报销规则 | 报销类型、金额上限、审批阈值、是否必须发票、费用科目 |
| 采购规则 | 采购类型、金额阈值、是否比价、是否验收 |
| 合同规则 | 合同分类、金额阈值、到期提醒天数、是否法务审批 |
| 用章规则 | 印章类型、使用范围、审批层级、附件要求 |
| 资产规则 | 资产分类、领用期限、归还提醒、报废审批 |
| 会议室规则 | 可预约时间、预约时长、取消规则、是否审批 |
| 办公用品 | 用品分类、库存预警值、申请上限、是否审批 |
| 审批规则 | 审批人为空、审批人等于发起人、超时、催办次数 |
| 消息规则 | 提醒频率、免打扰、归档、保留周期 |
| 文件规则 | 上传大小、类型白名单、预览类型、下载权限、保留周期 |
| 导入导出 | 单次导出上限、异步导出阈值、导出字段 |
| 报表口径 | 统计时间、部门口径、是否包含驳回/撤回/作废 |
| 编号规则 | 单据前缀、日期格式、流水号长度、按部门编号 |
| 页面体验 | 默认分页、默认排序、首页卡片、常用入口 |
| 安全策略 | 密码复杂度、会话超时、登录失败锁定、IP 白名单 |
| 审计策略 | 日志保留周期、敏感操作范围、导出审计范围 |

### 8.4 规则版本

规则变更不能影响历史单据。

要求：

- 每次发布规则生成规则版本。
- 业务单据提交时绑定当时规则版本。
- 历史单据按提交时规则展示和追溯。
- 新规则只影响新提交单据。
- 规则版本不可物理删除，只允许停用。

示例：

```text
4 月规则：报销 > 5000 需要总经理审批
5 月规则：报销 > 10000 才需要总经理审批

4 月提交的 8000 元报销：仍按旧规则，需要总经理审批。
5 月提交的 8000 元报销：按新规则，不需要总经理审批。
```

### 8.5 规则体验与审计

规则配置页面要求：

- 展示规则名称、适用业务、适用部门、适用角色、生效时间、失效时间。
- 提供自然语言说明。
- 发布前支持模拟测试。
- 重要规则修改必须填写变更原因。

```json

  "message": "OK",
  "data": {},
```

业务错误示例：

```json
{
  "code": "WORKFLOW_TASK_NOT_ASSIGNED_TO_USER",
```

### 15.3 接口原则

- 关键操作必须幂等。
- 审批、撤回、转交、加签必须有状态前置校验。
- 所有接口错误必须带稳定错误码。

## 16. 安全设计

### 16.1 基础安全

- 密码加盐哈希存储。
- 登录失败锁定。
- 会话超时。
- 统一认证与鉴权。
- 后端接口权限校验。
- 数据权限强校验。
- 防止 SQL 注入。
- 防止 XSS。
- 根据认证方式评估 CSRF 防护。
- HTTPS 部署。

### 16.2 审批安全

- 审批接口必须校验当前用户是否为当前任务审批人。
- 已处理任务不可重复处理。
- 已结束流程不可继续审批。
- 撤回与审批并发时必须有状态锁。
- 审批意见和动作不可随意删除。

### 16.3 附件安全

- 文件类型白名单。
- 文件大小限制。
- 禁止上传可执行文件。
- 附件下载必须走鉴权接口。
- 附件访问必须校验业务权限。
- 下载记录写入日志。
- 敏感附件禁止公开 URL 访问。

### 16.4 数据脱敏

- 手机号、身份证号、银行卡号、薪资类字段脱敏显示。
- 敏感字段导出需要额外权限。
- 不同审批节点可见字段不同。
- 审计日志中避免记录明文敏感数据。

## 17. 性能与容量

### 17.1 指标

| 指标 | 建议值 |
| --- | --- |
| 注册用户 | 1000+，预留 3000-5000 |
| 日常在线 | 100-300 |
| 常规接口响应 | 优先控制在 500ms 内 |
| 列表分页大小 | 默认 20，最大 100 |
| 单文件大小 | 20MB-50MB 可配置 |
| 日志保留 | 至少 180 天 |
| 数据库备份 | 每日自动备份 |

### 17.2 优化策略

- 用户权限、字典、系统参数使用 Redis 缓存。
- 待办列表按审批人、状态、创建时间建立索引。
- 业务列表按状态、发起人、部门、时间建立索引。
- 大数据导出走异步任务。
- 附件不存数据库，只保存元数据和路径。
- 日志表按时间归档。
- 避免列表接口 N+1 查询。
- 权限调整后需要清理权限缓存。

## 20. 细节设计清单

### 20.1 默认值与模板

- 常用申请提供默认模板。
- 表单默认带出申请人、部门、岗位、直属上级。

### 20.2 编号与打印

- 单据编号规则可配置。

- 支持打印模板。

### 20.3 草稿与防误操作

- 长表单自动保存草稿。
- 关闭页面或返回时提醒未保存内容。
- 高风险操作需要二次确认。
- 审批通过后不允许随意撤销。
- 删除类操作优先软删除或进入回收站。

### 20.5 问题定位

- 每个请求生成 `requestId`。
- 审批失败提示可理解的业务原因。

## 21. 最终版本开发策略

### 21.1 开发原则

本项目不按精简 MVP 或多期功能递增模式建设，而是按最终完整版本一次性设计、一次性开发、一次性验收。开发过程中可以按照工程依赖顺序推进，但交付目标以完整 OA 平台为准，不将采购、会议室、资产、办公用品等模块延后为后续版本。

核心原则：

- 需求一次性定稿：核心模块、权限、规则、流程、报表口径在编码前确认。
- 架构一次性到位：组织、权限、流程、规则、表单、消息、文件、审计、报表底座完整建设。
- 模块并行开发：平台底座稳定后，各业务模块并行接入统一能力。
- 统一验收上线：所有模块达到最终验收标准后整体上线。
- 不做临时简化方案：避免先写轻量逻辑、后续再大规模推翻重构。

## 22. 验收标准

### 22.1 功能验收

- 用户可登录、退出、修改密码。
- 管理员可维护组织、人员、岗位、角色、权限。
- 流程管理员可配置并发布流程。
- 规则管理员可配置金额阈值、工作时间、超时规则等。
- 员工可发起请假、报销、用章、采购、合同申请。
- 审批人可处理待办。
- 用户可查看流程进度。
- 系统可记录审批历史和流程轨迹。
- 公告可按范围发布并统计阅读情况。
- 附件可上传、下载，并受权限控制。
- 报表可按定义口径统计。

### 22.2 权限验收

- 普通员工不能访问后台管理。
- 部门负责人只能查看授权部门数据。
- 有查看权限不等于有审批权限。
- 非当前任务处理人不能审批。
- 无权限用户不能下载附件。
- 导出数据受数据权限控制。
- 权限变更写入审计日志。

### 22.3 流程验收

- 流程版本隔离正确。
- 条件分支判断正确。
- 会签全部通过后节点通过。
- 或签任一通过后节点通过。
- 加签、转交、委托记录完整。
- 撤回、驳回、终止状态正确。
- 审批人离职或为空时有兜底处理。
- 流程进度展示准确。
- 超时提醒和催办记录准确。

### 22.4 规则验收

- 金额规则能影响流程分支。
- 工作时间能影响请假时长计算。
- 节假日和调休日计算正确。
- 规则版本不影响历史单据。
- 规则变更有审计记录。
- 规则发布前可模拟测试。

### 22.5 性能验收

- 1000+ 用户数据量下系统可正常运行。
- 常规分页列表响应稳定。
- 待办列表查询稳定。
- 审批提交和处理不出现重复任务。
- 附件上传下载稳定。
- 批量导出不阻塞核心业务。

### 22.6 响应式验收

- PC 端支持完整功能。
- 手机端支持登录、待办、审批、公告、消息、详情查看。
- 主要页面在手机端不出现内容不可读或按钮无法点击。
- 复杂后台配置在 PC 端体验完整。

## 23. 风险与控制

| 风险 | 说明 | 控制措施 |
| --- | --- | --- |
| 范围膨胀 | 最终版开发容易不断增加模块 | 编码前冻结最终范围，变更进入评审 |
| 流程复杂度过高 | 审批规则多，测试量大 | Flowable + OA 适配层，建立流程用例集 |
| 权限越权 | 数据权限和审批权限混淆 | 后端统一权限校验，权限测试覆盖 |
| 历史数据错乱 | 组织、规则、流程变化影响旧数据 | 保存快照和版本 |
| 并发重复提交 | 双击、重复审批、并发撤回 | 幂等键、乐观锁、事务 |
| 附件泄露 | 文件 URL 被绕过访问 | 附件统一鉴权下载 |
| 报表口径争议 | 统计规则不清 | 提前定义报表口径 |
| 备份不可用 | 只备份不验证恢复 | 定期恢复演练 |
| 移动端期望过高 | 响应式不等于完整 App | 明确移动端功能边界 |
| 周期失控 | 底座和业务同时复杂 | 按依赖顺序开发，统一最终验收 |

## 26. 总结

本系统应按企业级 OA 平台设计，以组织人员、权限中心、通用流程审批引擎、规则配置中心、表单中心、消息待办、文件附件、审计日志和数据历史为核心底座。

业务模块不应各自独立实现审批、权限、消息、规则和附件能力，而应统一接入平台底座。这样后续新增请假、报销、合同、采购、资产等模块时，可以复用已有能力，减少重复开发和权限风险。

对于 1000+ 用户规模、不接第三方、Web 响应式的企业内部 OA，本项目按最终完整版本开发。系统必须控制边界：做企业级可配置 OA 平台，不做无限扩展的低代码平台。平台底座和业务模块均按最终版本建设，通过严格需求冻结、接口契约、联调测试和统一验收降低整体上线风险。
